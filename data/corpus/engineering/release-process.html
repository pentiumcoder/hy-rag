Release Process

This page describes how code reaches production through the weekly release train, how canary analysis works, and how to roll back.

The weekly release train

The release train departs every Tuesday at 09:00 UTC. Every change merged to main and green in staging by Monday 18:00 UTC is included. The release captain for the week, rotated across teams, cuts the release branch and posts the change list in #releases.

Production deploys are frozen on Fridays after 14:00 UTC and all weekend. The only exception is a fix for an active SEV1 or SEV2 incident, which needs explicit approval from the incident commander. A company-wide release freeze also runs for the last two weeks of December.

Canary analysis

Each service is rolled out in three stages:

  1. Canary: 5% of traffic for 30 minutes.
  2. 25% of traffic for 30 minutes.
  3. 100% of traffic.

Automated canary analysis compares the new version with the current one. A stage fails, and the rollout is stopped and reverted automatically, if either condition holds:

SignalRollback threshold
5xx error rateabove 1% of requests
p99 latencymore than 20% higher than the current version

Rolling back

To roll back a service manually, run:

nwctl rollback --service <service> --to <release-id>

Release IDs have the form rel-YYYYMMDD-N and are listed with nwctl releases --service <service>. A rollback does not revert database migrations; migrations must be backwards compatible with the previous release for exactly this reason.

Hotfixes

A hotfix is any production deploy outside the train. Hotfixes need a pull request with the hotfix label, the usual review approvals, and a passing staging deploy. They still go through canary analysis, but the stages are shortened to 10 minutes each.
